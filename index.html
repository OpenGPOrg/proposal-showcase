Background & Motivation

Why Volunteer Consumer GPUs Need a New Inference Architecture

High GPU infrastructure costs limit AI access outside well-resourced institutions, even while gaming GPUs and workstations sit idle. Pooling them for LLM inference introduces two coupled bottlenecks: tight VRAM limits and unpredictable node churn.

01 · Stateful Two-Phase Execution

Prefill vs. Decode

  • Prefill: Processes all input tokens in parallel; compute-intensive; initializes the Key-Value (KV) cache; measured by Time to First Token (TTFT).
  • Decode: Generates tokens autoregressively one by one; memory-bandwidth intensive; KV cache grows per token in every layer; measured by Time per Output Token (TPOT).

02 · Memory Bottleneck

Weights & Growing KV Cache

  • Model weights: Llama 3.3 70B requires 140 GB in FP16 (40 GB in Q4_K_M); Llama 4 Scout 109B MoE requires ~218 GB in FP16 (~55 GB in Q4_K_M).
  • KV cache growth: On Llama 3.1/3.3 70B (16-bit), KV cache reaches 10 GiB at 32K context and 40 GiB at 128K context—exceeding 24 GB consumer GPUs.

03 · Distribution Strategy

Model Pipeline Parallelism

Model layers are partitioned into sequential stages assigned across nodes. Adjacent nodes exchange only intermediate activations, allowing models larger than any single GPU to execute across consumer devices.

04 · Volunteer Computing Reality

Heterogeneous & Dynamic Peers

Unlike CPU volunteer projects (GIMPS, BOINC-SETI@home), volunteer GPU networks combine diverse VRAM capacities, hardware, and network speeds—and peers can join or leave unexpectedly mid-job.

Problem Statement

How to enable organizations to run LLM inference across volunteers' personal devices without the system crashing from limited memory or losing expensive progress when volunteers unexpectedly disconnect?

Literature Review & Research Gap

Existing Distributed LLM Systems Leave a Clear Gap

Prior work addresses scheduling, memory offloading, or interactive fault tolerance in isolation, but none combines consumer GPU support, batch execution, bounded VRAM, and decentralized in-flight recovery.

Scheduling & Allocation

Parallax, HexGen, SpotServe

  • Parallax: Two-phase scheduling (DP + water-filling) on consumer devices; 3.6× throughput, 3.2× lower latency, but no fault tolerance.
  • HexGen: Asymmetric partitioning for datacenter GPUs; 2.3× lower latency, 4× request rate, datacenter-only and no fault tolerance.
  • SpotServe: Dynamic reparallelization on cloud spot instances; 2.4× lower latency, requires cloud grace period.

Fault Tolerance (Closest: Petals)

Client-Bound Recovery

  • Petals: Client caches hidden activations and re-routes to a replacement server for full KV re-prefill; recovery speed is bottlenecked by client bandwidth.
  • Parallax, MeshLLM, DeServe: No in-flight fault handling—node dropout causes total job loss.

Memory & KV Management

FlexGen, Prima.cpp, DeServe

  • FlexGen: VRAM → CPU RAM → Disk offloading; OPT-175B-INT4 on 16 GB VRAM at 1 tok/s, single node only.
  • Prima.cpp: Ring parallelism on 4 consumer devices (Llama-70B-Q4K at 674 ms/tok), high TTFT, no fault tolerance.
  • DeServe: PCIe full-duplex KV offloading/onloading; 12.6× throughput, single pipeline per client, no fault tolerance.

Objectives & Hypotheses

Research Goals & Quantitative Experimental Design

Domain: Distributed/Decentralized Systems for ML inference serving · Nature: Problem-Solving & Development · Approach: Quantitative Experimental.

Project Objectives

Four Core Deliverables

  1. Design and develop a peer-to-peer volunteer computing system for distributed LLM batch inference.
  2. Develop an error-code-based fault-tolerance mechanism to handle node churn during inference.
  3. Integrate KV-cache offloading strategies to reduce GPU VRAM load.
  4. Evaluate the developed system and mechanisms against established baselines.

Formal Hypotheses

Testable Claims

  • H1 (Recovery Latency): Decentralized activation-based fault tolerance reduces recovery time compared with Petals' client-based mechanism.
  • H2 (Context Capacity): Query-aware bounded-KV cache streaming enables larger batch contexts within fixed physical VRAM without quantization loss or OOM crashes.
  • H3 (Throughput Resilience): The combined system sustains higher aggregate batch throughput under simulated volunteer churn than reactive-reroute or fail-closed baselines.
Proposed Methodology

System Architecture & Core Mechanisms

OpenGP separates GPU pipeline execution from erasure-coded checkpoint storage and keeps per-node VRAM bounded via query-aware KV cache streaming.

Preliminary Experiment

Measuring Network Hop Latency Across Consumer GPUs

A 2-node University TCP testbed evaluated how multi-hop pipeline parallelism affects interactive latency and decode throughput on consumer hardware.

2 Nodes

RTX 3060 (6 GB) + RTX 4070 Ti (16 GB) over TCP

Qwen2.5-7B

Instruct, 28 layers, full FP16, 100% GPU VRAM

1 – 9 Hops

Tested across Large Context, Medium & Small Chat

> 100 ms

Inter-token latency at ≥ 5 hops (infeasible for chat)

Key Finding

Network hops compound sequential decoding latency: at ≥ 5 hops, inter-token latency exceeds 100 ms, rendering interactive chat infeasible and experimentally justifying OpenGP's focus on non-interactive batch inference.
