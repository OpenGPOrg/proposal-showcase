Background & Motivation

Why Volunteer Consumer GPUs Need a New Inference Architecture

High GPU infrastructure costs limit AI access outside well-resourced institutions, even while gaming GPUs and workstations sit idle. Pooling them for LLM inference introduces two coupled bottlenecks: tight VRAM limits and unpredictable node churn.

01 · Stateful Two-Phase Execution

Prefill vs. Decode

  • Prefill: Processes all input tokens in parallel; compute-intensive; initializes the Key-Value (KV) cache; measured by Time to First Token (TTFT).
  • Decode: Generates tokens autoregressively one by one; memory-bandwidth intensive; KV cache grows per token in every layer; measured by Time per Output Token (TPOT).

02 · Memory Bottleneck

Weights & Growing KV Cache

  • Model weights: Llama 3.3 70B requires 140 GB in FP16 (40 GB in Q4_K_M); Llama 4 Scout 109B MoE requires ~218 GB in FP16 (~55 GB in Q4_K_M).
  • KV cache growth: On Llama 3.1/3.3 70B (16-bit), KV cache reaches 10 GiB at 32K context and 40 GiB at 128K context—exceeding 24 GB consumer GPUs.

03 · Distribution Strategy

Model Pipeline Parallelism

Model layers are partitioned into sequential stages assigned across nodes. Adjacent nodes exchange only intermediate activations, allowing models larger than any single GPU to execute across consumer devices.

04 · Volunteer Computing Reality

Heterogeneous & Dynamic Peers

Unlike CPU volunteer projects (GIMPS, BOINC-SETI@home), volunteer GPU networks combine diverse VRAM capacities, hardware, and network speeds—and peers can join or leave unexpectedly mid-job.

Problem Statement

How to enable organizations to run LLM inference across volunteers' personal devices without the system crashing from limited memory or losing expensive progress when volunteers unexpectedly disconnect?
